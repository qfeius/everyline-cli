# 设计：审查清单对话分页

## 现状

Skill 会读取全部清单，但没有规定宿主选择控件容量超限时的交互状态。Codex 或 WorkBuddy 可能只把部分清单放入一次选择卡片，并同时加入立场方问题，界面的 `1/2、2/2` 实际表示两个问题而不是清单分页。

## 方案

- 查询完全部 CLI 分页后冻结候选顺序：内置规则包固定编号 `0`，真实清单从 `1` 连续编号。
- 真实清单按 4 项一页切分，页码基于完整真实清单数量计算；翻页期间不重新查询或重新编号。
- 会话状态保存当前页和完整编号映射。每次交互展示当前页与总页数。
- 导航动作包括上一页、下一页和按名称搜索。完整名称输入在全量候选中匹配，不受当前页限制。
- 用户一次回复一个或多个有效编号或唯一名称后立即冻结清单状态；下一次独立交互展示立场方候选，不增加完成或确认步骤。
- Codex 当前回合提供原生结构化选项工具时，符合容量的立场方和强度使用互斥单选选项卡；当前单选工具不承载清单多选、分页和搜索，也不为取得工具而切换协作模式。

## 兼容性

CLI 命令、JSON 输入、编号到 ID 的映射和任务请求结构均保持不变。清单数量不超过 4 时仍只显示一页，但清单和立场方仍分为两个阶段。Codex 当前模式没有原生选项工具时使用与豆包相同的编号文字回退。

## 风险与回滚

- 翻页时若重排候选会造成编号错配，因此候选集合在首次完整查询后必须冻结。
- 多选必须在同一次回复中完整解析，且稳定全局编号可以引用此前浏览页面中的清单。
- 回滚只需恢复 Skill 与文档，不涉及后端或用户数据。
